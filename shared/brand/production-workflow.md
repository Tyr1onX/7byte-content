# 7BYTE 固定视频工作流

这份文档是 7BYTE 后续每一期视频的默认生产流程。除非明确决定升级品牌/流程，否则新视频按此执行，不重新发明一套做法。

## 0. 每一期必须留下记录

每个 `episodes/<episode>/` 必须有：

- `idea.md`：本期核心问题与观众要记住什么。
- `script.md`：最终口播稿。
- `storyboard.md` / `animation-spec.md`：动画设计与时间轴。
- `cover/cover.json`：本期封面内容配置。
- `publish.md`：最终发布记录（标题、简介、话题、封面、声音、成片、发布日期、数据复盘等）。

发布后不删除历史记录；若后续重发/修改，在 `publish.md` 追加新版本。

## 1. 选题

先确定一个观众能立刻理解的问题：

> 这条视频到底回答什么？

一条视频只解决一个主问题，不为了“完整”堆过多知识点。

## 2. 口播稿

- 先把内容写到单独听也能理解。
- 使用自然口语，不像教材朗读。
- 先保证表达舒服，再决定最终时长，不机械卡 60 秒。
- 技术术语保持准确，例如 DNS / HTTPS / HTTP / HTML / CSS / JavaScript。

## 3. AI 人声

- 先选定最终声音，再做最终动画 timing。
- 不在已经带声音的视频上重复叠加新声音。
- 每一期在 `publish.md` 记录实际使用的 voice / rate。
- EP001 当前基准声线：`zh-CN-YunyangNeural`。

## 4. Motion Canvas 动画

- 以最终人声为时间轴调整画面，而不是平均分配秒数。
- 动作本身保持利落，时长主要通过关键状态停留来匹配口播。
- 一次只强调一个主运动对象。
- 每个动画都必须帮助解释因果，不为了“科技感”而动。
- 最终正文：`1080×1920 / 60fps`。

## 5. 固定动态片尾

**唯一权威版本：EP001 V5 已认可成片中的片尾。**

- 长期文件库：`/7BYTE/brand/7BYTE-outro-canonical-from-EP001-V5.mp4`。
- 后续视频直接复用，不重新生成、不根据描述复刻。
- 头像尺寸、圆环、7 个 Byte 方块、`7BYTE_`、标语、终端提示、位置、节奏全部冻结。
- `shared/brand/outro-template.py` 只能复制 canonical 资产，不能设计新片尾。

## 6. 字幕：两条正式路线，二选一

程序化正文默认不烧字幕。每一期在 `publish.md` 记录最终使用哪条字幕路线。

### A. 7BYTE Auto Subtitle Skill

优先读取 `skills/auto-subtitles.md`。

- 用最终旁白或最终 MP4 做 ASR。
- 自动生成 SRT，并保留准确时间戳。
- 重点检查 DNS / HTTPS / HTTP / GET / HTML / CSS / JavaScript 等技术词。
- SRT 导入剪映后，只做字体、字号、位置等视觉调整。
- 适合以后继续自动化生产。

### B. 剪映「识别字幕」

- 直接用最终人声识别。
- 检查明显错字、断句和技术词。
- 适合剪映识别已经足够准确、希望少一步文件流转时。

**不要同时做两套再长期保存两份。** 哪条更省事、更准确就用哪条。

字幕审阅器保留为异常情况下的备用工具，不是默认必经步骤。

## 7. 固定封面系统

每一期必须同时准备 **两张封面**：

### 竖封面
- 比例：`3:4`。
- 用于抖音竖封面入口。

### 横封面
- 比例：`4:3`。
- 用于抖音横封面入口。

### 两张封面的共同规则

固定：
- 黑/炭灰背景。
- 暖白主文字。
- `#D8FF68` 荧光绿作为少量强调。
- 使用唯一权威抖音头像 + `7BYTE` 品牌标识。
- 版式简洁、高对比、第一眼能读懂。

每期变化：
- 本期核心问题/标题。
- 与本期内容直接相关的一个主视觉。

禁止默认加入：
- `EP001 / EP002` 等编号。
- `INTERNET / SERIES` 等系列标签。
- 无意义角标、分类标签、装饰性小字。
- 大量流程文字或为了显专业堆信息。

封面的判断标准只有一个：**缩小后，观众一眼能知道这条视频讲什么。**

## 8. 发布信息

发布前必须确定并写入本期 `publish.md`：

- 作品标题。
- 作品简介。
- 话题标签（一般 3–5 个，相关性优先）。
- 合集（如适用）。
- 自主声明/AI 内容标记（按平台实际选项处理）。
- 竖封面文件。
- 横封面文件。
- 最终成片文件。
- 字幕路线。
- 发布日期。
- 发布链接（能获取后补上）。

### 文案原则

- 标题直接回答“这条视频讲什么”，不要标题党到失真。
- 简介用 1–3 句补充价值，不重复整段口播。
- 话题只放真正相关的，不蹭无关热词。
- 不为了填满平台字段增加多余信息。

## 9. 发布前检查

- [ ] 最终视频 1080×1920 / 60fps。
- [ ] 只有正确的一条主旁白轨，不存在叠音。
- [ ] 没有程序内旧字幕残留。
- [ ] 字幕路线已确定，并检查技术词/断句。
- [ ] 使用 canonical 片尾，没有旧版/临时片尾残留。
- [ ] 竖 3:4 和横 4:3 两张封面都已准备。
- [ ] 两张封面没有 episode 编号、系列标签等冗余信息。
- [ ] 标题、简介、话题已记录到 `publish.md`。
- [ ] 成片和两张最终封面已存长期文件库，不只存在 `/mnt/data` 临时目录。

## 10. 长期存储：只保存真正有用的发布资产

### ChatGPT 文件库

每期默认只长期保存：

```text
/7BYTE/EPxxx/
├─ final.mp4
├─ cover-vertical-3x4.png
└─ cover-horizontal-4x3.png
```

品牌目录只保存真正跨期复用的二进制资产：

```text
/7BYTE/brand/
├─ douyin-avatar-original.png
└─ 7BYTE-outro-canonical-from-EP001-V5.mp4
```

默认**不长期保存**：
- 中间渲染视频 / preview。
- 失败版和旧版封面。
- TTS 声音试听包。
- subtitle review JSON。
- ASR verbose JSON / word timestamps。
- 临时 WAV / WebM。
- 重复的 reference 文件。
- 品牌 ZIP 备份（源码已经在 GitHub）。
- 最终 SRT（除非确实需要跨软件复剪/归档）。

### GitHub

长期保存：
- 可复现源代码和真正使用的自动化。
- 品牌规则与 skills。
- 每一期 `idea/script/storyboard/animation-spec/cover config/publish.md`。

GitHub 不用来堆每次导出的二进制成片、试听包和临时文件。

### `/mnt/data`

只是当前 ChatGPT 工作环境临时副本，不能视为长期存储。

## 11. 发布后数据测试

单条视频发布后，不因为早期数据不理想立刻推翻内容体系。每一期在 `publish.md` 留下数据记录，用多条视频形成可比较样本。

至少记录：
- 播放量。
- 点赞 / 评论 / 收藏 / 分享（平台能看到什么就记什么）。
- 完播率、平均播放时长等平台可见观看指标。
- 主页访问 / 新增粉丝等转化指标（平台能看到时记录）。
- 观察时间点，例如 24h / 72h / 7d。

EP001 是新账号的第一条正式样本，先作为 baseline，不单独把它当作账号长期表现结论。
