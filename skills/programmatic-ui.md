# Skill: Programmatic UI vs Real Capture

## 默认

能准确复现、且真实 UI 本身不是内容重点时，优先程序化 UI。

适合程序化复现：
- 浏览器外框、地址栏、加载状态。
- 终端窗口。
- HTTP request/response 面板。
- 文件/代码编辑器的抽象界面。
- 网络节点、状态卡、决策流程等解释型 UI。

适合真实录屏：
- “真的输入 baidu.com 后页面出现”这种真实行为。
- 某个软件具体按钮/交互就是知识点本身。
- 需要证明某个现象确实存在。

## 目标

减少重复手工录制，但不为了省事牺牲可信度、空间逻辑或视觉质量。

程序化 UI 必须：
- 文案准确。
- 布局像真实产品逻辑，不做 AI 风假 UI。
- 不伪造会被观众误认为真实截图的数据。
- 每个元素都承担明确的信息功能。

## 1. 画面文字不能充当“第二套字幕”

旁白 + 字幕已经负责完整句子。画面里的文字只负责**补充视觉结构**：

适合：
- 实体名：`路由器`、`DNS`、`网站服务器`。
- 状态：`断线`、`失败`、`信号强`。
- 关系：`手机 ↔ 路由器`。
- 简短结论模型：`Wi-Fi 图标 → 本地无线链路`。
- 决策结果：`多个设备都失败 → 优先检查网络侧`。

不适合：
- 把当前旁白完整再写一遍。
- 把字幕换几个词后放在标题/说明条里。
- 同一时刻同时出现“标题句 + 说明句 + 字幕句”，三遍表达同一个意思。

判断：如果删掉某段画面文字后，观众对**关系、状态、位置或决策**没有损失，就删除它。

## 2. 不动画长文本内容本身

禁止用长句执行 `text(newText, duration)` 这种字符串插值来承担镜头切换；过渡中容易出现不可读的中间文本。

正确方式：
1. 旧文字淡出。
2. 直接替换文本，或切换到另一个 shot。
3. 新文字淡入。

更优先：让不同概念使用独立 shot，而不是让一个全局 headline 在整条视频里不断变字。

## 3. 连线必须由节点位置驱动

网络图、流程图、依赖图的 connector 禁止手写“看起来差不多”的静态坐标段。

必须满足：
- Line 的端点由目标节点的 `left/right/top/bottom` 等几何信号计算。
- 节点移动、缩放或尺寸改变时，连线自动跟随。
- connector 与其节点放在同一个 shot/group 中；group 隐藏时 connector 一起隐藏。
- 不允许无 ref、无 opacity 管理的“常驻小线段”。
- 不用多段短线假装一条连接；需要断点时使用明确的状态标记。

如果无法可靠绑定，就改用 Layout/Flexbox 固定节点后再连线，不继续叠绝对坐标。

## 4. 优先稳定布局，不优先炫技

对解释型 UI：
- 多节点关系优先 `Layout/Flexbox` 或固定网格。
- 一个 shot 内节点尽量不改变尺寸和拓扑。
- 大的结构切换优先 shot-to-shot 淡出/淡入，而不是同时移动 5 个节点去“变形”成另一套图。
- 需要保持品牌一致时，复用同一个组件定义，不复用一套越来越复杂的运行时状态。

## 5. Shot 必须自包含

每个 shot 应该有自己完整的：
- 实体。
- 连线。
- 状态标记。
- 说明标签。

镜头退出时整个 group 一起隐藏。不要让上一镜头的 connector、chip、辅助线残留到下一镜头。

## 6. 最终视频必须做视觉审计

源码通过 TypeScript / build 只说明“能运行”，不说明“画面正确”。

最终成片必须抽帧检查：
- 第 0 帧 / 前 1 秒：是否有未初始化残留。
- 每次 shot 切换前后。
- 节点最多、连线最多的一帧。
- 每个故障状态。
- 字幕最长的帧。
- 最后 2 秒正文与片尾交界。

必须人工/视觉模型检查：
- 连线是否真的接到节点边缘。
- 元素是否重叠。
- 文字是否与字幕重复。
- 是否出现孤立线条、幽灵元素、上一 shot 残留。
- 结尾是否意外回到开头。

发现错误必须回到 scene/layout 修复，不能只在最终视频上遮盖。
