# Design Notes

## 当前状态
EP.001 的首版、V2 都只视为视觉探索。能运行、能动，不等于视觉成立。

在用户明确认可 EP.001 的视觉质量之前：
- 不把本期组件提升到 `shared/`。
- 不把本期视觉细节固化成全局设计系统。
- 允许在本期内部继续重做，先证明效果，再谈复用。

## 这期不要什么
- 不用蓝紫渐变、粒子网络、赛博背景。
- 不为了显专业展示 SYN/SYN-ACK/ACK；第一期只讲“大流程”。
- 不快速切很多独立卡片。
- 不再使用 `7BYTE / INTERNET 001`、`01 / DNS`、`02 / CONNECT` 这类重复章节 chrome。
- 不同时出现“品牌标签 + 步骤标签 + 大标题 + 解释文字”四层信息。
- 不使用超大标题占掉核心动画空间。
- 不使用横向桌面信息图再硬塞进 9:16。
- 不让任何重要文案接近画布边缘；单行重要文案必须天然短到不会溢出。

## V3：竖屏原生构图
- 输出仍固定 `1080 × 1920`，因为当前问题首先是构图而不是 9:16 本身。
- 主内容安全宽度 `900px`，左右至少保留 `90px`。
- 页面只保留一组简短叙事文案：一行主句 + 一行辅助句。
- 核心动画始终占据中部大部分空间，不再被章节编号和装饰标签抢位置。
- 网络流程改成**上下方向**：浏览器在上，DNS / Server 在下，请求向下、响应向上。
- 浏览器 → DNS → Server 通过同一条中心网络路径建立空间连续性。
- 整期网络阶段只允许一个主运动 packet。
- 所有重要对象尽量沿画面中轴组织，避免左右两侧同时堆 UI 导致遮挡。

## 浏览器 UI
- 浏览器只保留知识点需要的 chrome：返回、刷新、地址栏、域名、菜单。
- 地址栏内部使用 Motion Canvas `Layout`，域名文本使用可伸缩宽度，不再手算输入光标位置。
- 网页主体保持简洁、接近真实搜索页逻辑：品牌、搜索框、按钮、内容骨架。
- HTML / CSS / JS / IMG 返回后必须分别改变同一个浏览器页面状态。
- 图标优先使用成熟 Iconify / Lucide 资源，不再临时画 `LOCK` 等假 UI。

## 视觉语言
- 背景：`#0F100E`。
- 主文本：暖白 `#F4F1E8`。
- 主强调色：`#D8FF68`，只用于网络状态和关键运动对象。
- 网页区域可以使用真实产品语义需要的局部品牌色，例如百度蓝；不扩散成整期装饰色。
- 不依赖 glow、模糊、玻璃拟态制造“高级感”。清晰度、层级和运动逻辑优先。

## Motion language
- 动画本身解释因果：域名请求下行到 DNS → IP 返回；请求下行到服务器；资源上行到浏览器。
- 大型对象进入使用轻微 scale + opacity / spring，避免突然出现。
- 普通路径移动约 0.85–1.1s；重要结果保留 0.4–0.9s 阅读时间。
- 不做无意义横向飞卡；运动方向应与网络关系一致。
- 浏览器在流程中始终是同一个对象，最后回到中心完成渲染。

## 清晰度与 Pages 验收
- 视觉验收必须使用 `1080 × 1920`、`resolutionScale = 1`。
- Pages Player `quality = 1`。
- Pages 预览页必须按浏览器**高度**和宽度共同约束 9:16 Player，整个画面一次完整显示，不允许用固定宽度导致桌面浏览器只看到视频上半截。
- Pages 页面本身不再显示额外的 EP 标题、分辨率标签、说明文字，避免和真正的视频画面混淆。

## 横屏备选
16:9 不是禁用方案。如果 V3 在竖屏原生布局下仍然无法让浏览器 + 网络流程获得足够空间，可以切换到横屏。但不能因为当前实现排版失败就直接把问题归因于 9:16；应先验证真正的竖屏构图。

## 真实 UI 决策
开头优先使用高质量程序化 BrowserFrame，因为可控、可重复。若后续对比确认真实录屏明显更自然，可以只替换真实浏览器首尾，中间解释流程继续保持程序化动画。
