# EP008 Core — 文件都删了，为什么还能恢复？

## 核心问题

文件已经删除、甚至清空回收站后，为什么恢复软件有时仍能找回来？

## 观众只需要记住

**普通删除通常不等于立刻把数据内容全部擦掉。** 文件系统会先让原来占用的空间变成“可再次使用”；在这些空间被新数据覆盖或底层存储完成回收前，旧内容有时仍可能残留。

## 事实链路

1. 文件系统既管理“这个文件叫什么、在哪里”，也管理底层哪些存储区域属于它。
2. 删除文件时，系统通常先更新文件系统元数据，并把原先占用的空间释放为可再次分配。
3. 这不等于底层每个数据字节会立刻被重写为零。
4. 因此，在旧数据尚未被覆盖的情况下，恢复工具可能通过扫描残留的数据结构或内容找回一部分文件。
5. 机械硬盘上，“覆盖之前仍可能恢复”是比较直观的情况。
6. SSD 还存在 TRIM / unmap：系统可通知底层存储，某些因删除而释放的块已经不再需要；控制器随后可以回收这些块，因此 SSD 上删除后的恢复通常更困难、更不确定。

## 本期边界

- 不承诺“删掉的文件一定能恢复”。
- 不把回收站机制当成核心；本期讨论的是已经绕过/清空回收站后的底层逻辑。
- 不深入 NTFS MFT、文件碎片、日志恢复、闪存垃圾回收等实现细节。
- 不把 SSD 说成“删除后立刻物理清零”；只说明 TRIM 会通知底层释放块，后续回收使恢复更困难。
- 不提供取证、绕过安全删除或恢复他人数据的操作教程。

## 可复用结论

- `删除 ≠ 立即抹掉每个字节`
- `可恢复 ≠ 一定能恢复`
- 想恢复自己的误删文件：越早停止向该盘继续写入，覆盖旧数据的概率越低。
- 真正需要隐私清除时，普通“删除文件”不等于安全擦除。

## 事实核对

Microsoft Windows 的 `fsutil behavior` 文档将 delete notification（TRIM / unmap）描述为：通知底层存储设备哪些集群因文件删除操作而被释放；NTFS 默认启用 TRIM，除非管理员禁用。该事实用于限制本期 SSD 部分的表述边界。
